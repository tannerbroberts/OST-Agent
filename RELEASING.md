# Releasing

OST-Agent is not published anywhere. A release is a git tag plus a rebuilt
bundle, and users get it by updating the plugin.

1. `npm test` and `npx tsc --noEmit` — both clean.
2. Bump `version` in `package.json`, `.claude-plugin/plugin.json`, AND `VERSION`
   in `src/index.ts`. All three must match; `test/release/version.test.ts`
   enforces it.
3. `npm run bundle` — rebuilds `dist/ost-agent.mjs` **and** regenerates
   `dist/capability-manifest.json` from it (the manifest step is chained, so it
   cannot be forgotten at the one moment it would be wrong).
4. Commit the bump, the rebuilt bundle and the regenerated manifest together. CI
   fails the build if the committed bundle does not match a fresh one, and
   `test/release/capability-manifest.test.ts` fails if the manifest does not
   describe the artefact committed beside it.
5. Update `CHANGELOG.md`.
6. `git tag vX.Y.Z && git push --tags`.

There is no publish step. There is no npm package. `package.json` is `private`,
so `npm publish` fails at the client before it reaches the registry.

## The capability manifest

`dist/capability-manifest.json` is the published list of everything the shipped
artefact can be asked to do: every MCP tool a session can call and every CLI
subcommand the binary answers to, each fingerprinted by its argument shape, plus
the artefact's own SHA-256 and byte length. It is generated by *running the
artefact and asking it* — never from `MCP_TOOL_NAMES`, because a list checked
against itself cannot catch the drift this exists for.

An operator verifies a release with:

```bash
shasum -a 256 dist/ost-agent.mjs          # matches manifest.artifact.sha256
node dist/ost-agent.mjs capability-manifest # re-derives the surface, exits 1 on divergence
```

## Signing a release (a key a person holds)

The manifest is **unsigned** today, and the file says so rather than implying
otherwise. Signing needs a private key, and no key can live in this repository:
one that anybody could clone could be used by anybody to re-sign a rewritten
manifest, which is worse than being unsigned because it looks signed.

To sign, a maintainer generates a key once, keeps the private half off this
machine's repository, and commits only the public half:

```bash
openssl genpkey -algorithm ed25519 -out ost-release.key   # keep this out of the repository
OST_RELEASE_SIGNING_KEY=ost-release.key npm run manifest  # signs the manifest it writes
```

The signature and the public half it was made with are then both in
`dist/capability-manifest.json` under `signature`. Copy that
`signature.publicKey` value (base64 SPKI) into `.claude-plugin/release-key.pub`.
From that commit on, an unsigned or
wrongly-signed manifest **fails the release**: `verifyRelease` treats a published
trusted key as a requirement, not a hint. Operators who obtained the key out of
band should pass their own copy instead — `node dist/ost-agent.mjs
capability-manifest --key /path/to/their.pub` — because a key that travelled
with the artefact was written by whoever wrote the artefact.
